## 二、当前卡点（核心）

```
A430: no IOMMU, fallback to VRAM carveout!
a4xx_gpu_init: *ERROR* No memory protection without IOMMU
mdp5_kms_init: no iommu, fallback to phys contig buffers for scanout
```

- 显示靠 **VRAM carveout** 能出图；但 **GPU 没有 IOMMU → Mesa/freedreno 无法分配/提交缓冲区** → 用户态只能 `swrast`/`llvmpipe`
- 实测：`glxinfo -B` → `Device: llvmpipe (LLVM 20.1.2)`, `Accelerated: no`；Xorg `AIGLX: Screen 0 is not DRI2 capable` → `DRISWRAST`；无进程映射 `msm_dri.so`
- 内核侧驱动**有**：`CONFIG_ARM_SMMU=y` + `CONFIG_QCOM_IOMMU=y`（`drivers/iommu/arm/arm-smmu/qcom_iommu.c`）
- **缺的是 DT**：`arch/arm64/boot/dts/qcom/msm8994.dtsi` 里 `iommu|smmu` **零命中**
- **上游主线也没有**：主线 `msm8994.dtsi`（25.5KB）grep `iommu|smmu` **0 命中**；`msm8992.dtsi` 仅 1KB（include 8994）
  → **没有任何现成参照可抄**

## 三、关键路径（建议分阶段）

**Phase 1：拿到 msm8994 IOMMU 的硬件参数（基址 / 中断 / 类型）**
- 需要确定：8994 的 GPU/MDP IOMMU 属于 **ctx-bank 风格（`qcom,msm-iommu-v1/v2`）** 还是 **SMMU-500 风格（`qcom,smmu-v2`）**
- 参数来源候选：
  1. 原厂固件：FFU 的 MainOS/PLAT 分区（`.sys` / 配置 blob）
  2. downstream Android 内核的 msm8994 DT（高通分支）
  3. 对照件：本树 `msm8916.dtsi` 的 `gpu_iommu: iommu@1f08000`（qcom,msm-iommu-v1 样式）+ `msm8996.dtsi` 的 `adreno_smmu/mdp_smmu`（qcom,smmu-v2 样式）
  4. AC/ACPI 表（FFU 内）中的设备树描述
- 产出：**IOMMU 硬件参数表**（节点地址、context bank、中断号、时钟、power-domain）

**Phase 2：补 DT 并验证内核侧**
- 在 `msm8994.dtsi` 增加 IOMMU 节点（参照 Phase 1 结论的样式）
- 给 `gpu@fdb00000`、`mdss@fd900000`、`mdp@fd901000` 增加 `iommus = <&... cb>` 属性
- 重编 dtb → 部署 → 验证：内核日志中 **"no IOMMU" 消失**、出现 SMMU 初始化信息

**Phase 3：用户态验证**
- `/dev/dri/renderD128` 出现 → `eglinfo`（GBM 平台）不再报 `eglInitialize failed`
- 期望 `EGL driver name: freedreno` / `glxinfo` `Device: fd430`（或类似）
- 裸测顺序：只读工具优先（`eglinfo`/`glxinfo`），**禁止** 用抢 DRM master 的工具（kmscube 已证实会把整机冻死）

**Phase 4：桌面切换 / 体验**
- Wayland（Phosh/wlroots）优先（无 Xorg 中间层）；X11 需让 Xorg 正常探测 `modesetting` + glamor（避免回退 fbdev）
- 候选桌面：**KDE Plasma Mobile**（Ubuntu 源里有 5.27.11，arm64）

**Phase 5（加分项 / 真正"没人干过"的价值）**
- 把 msm8994 IOMMU 的 DT 节点**上游化**（提交 LKML）——这是可写进履历的实打实贡献

## 五、方法论 / 已知坑（别人踩不到，写文档时是亮点）

1. **真机探针必须写持久文件**（`/home/lumia/probe.log` + `fsync`）——该平台是"静默复位"，`printk` 复位即丢
2. **禁止在自旋锁（关中断）区内做文件 IO**（`filp_open`/`kernel_write`/`vfs_fsync` 会睡眠）→ 原子上下文睡眠 → 死锁/静默复位。已给探针宏加 `if (!in_atomic() && !irqs_disabled())` 保护
3. **测试 GPU 只用只读工具**：`kmscube` 抢 DRM master 会导致整机冻死（输入全死）
4. **systemd 服务排序**：任何依赖 DRM 的服务必须 `After=p13.service`（msm 由 p13 里 `modprobe` 加载，DRM 节点在其后才出现）；`Before=ssh.socket` 会造成 ordering cycle（曾导致 sockets.target 被跳过）
5. **离线镜像调试流程**：手机 eMMC 挂到 PC → 改 rootfs（内核模块/服务）→ 卸载 → 手机开机验证 → 日志回读
6. **设备名会漂移**（sda/sdb/sdc）→ 用 `lsblk -rno NAME,PARTLABEL | awk '$2=="rootfs"'` 取；旧挂载会 stale，先 `umount -l`
7. **手机无 RTC**：journal/probe.log 时间戳不可信，只能靠顺序
8. 手机 rootfs 装包：PC 上用 `qemu-aarch64-static` + chroot（手机自身无网络）

### 7.1 已确认（两边一致）
- MSM8994 的 IOMMU = **Qualcomm MSM IOMMU v1 / context-bank 风格**，**不是 SMMU-500**
  - 我侧证据：`drivers/iommu/arm/arm-smmu/qcom_iommu.c` 只匹配 `qcom,msm-iommu-v1`；`Documentation/devicetree/bindings/iommu/qcom,iommu.txt` 同款
  - 下游命名 `qcom,msm-smmu-v1` = 上游 `qcom,msm-iommu-v1` 的重命名（同代硬件）
- 下游结构分层：父 IOMMU（v1）+ `qcom,msm-smmu-v1-ctx` 子节点（靠 `label` + `qcom,iommu-secure-id` 区分）
- 8992 / APQ8084 同族均有 iommu dtsi（可作结构参考，**不可复制地址/SID**）

### 7.2 已验证可用的数据（下游）
| 项 | 值 |
|---|---|
| MDP IOMMU base | `0xfd9cc000`（+`reg-names="iommu_base"`，`0x10000`） |
| MDP IOMMU 中断 | SPI 73 / 229 / 230 / 232 |
| MDP IOMMU 供电/时钟 | `vdd-supply=<&gdsc_mdss>`；`clk_mdss_axi_clk` + `clk_mdss_ahb_clk` |
| MDP ctx（示例片段） | `ctx@fd9d4000`，SPI 47，SID 0，`label="mdp_0"` |
| **GPU IOMMU 引用** | `vdd-supply=<&gdsc_oxili_cx>`、`alt-vdd-supply=<&gdsc_oxili_gx>`、`secure-id=18`、`clk_oxili_gfx3d_clk` + `clk_oxilicx_ahb_clk` |
| GPU 侧联动 | `msm8994-gpu.dtsi` 里 `vdd-supply=<&gdsc_oxili_gx>`、`iommu=<&kgsl_iommu>` |

⚠️ **注意区分**：GPT 文档里 `0xfda64000 / ctx@fda6c000 / 中断70,71` 那组是**示例占位**，非 8994 真实值（GPT 已声明）。

### 7.3 我方关键判断（比下游文档更重要）
> **主线不需要下游 KGSL IOMMU 驱动。** mainline msm/adreno 走**通用 IOMMU API**：GPU 节点带 `iommus` + 任一可用 provider（`qcom_iommu` = `qcom,msm-iommu-v1`）即会 `iommu_domain_alloc` + `iommu_attach_device`。
> → 移植策略 = **抄数据（GDSC/时钟/ctx 地址/中断/SID），不抄驱动与 compatible**。

## 八、GPT 深度研究结果 vs 我方取证（2026-09-21 02:07）

原文存档：`950xl-iommu-docs/gpt-deepresearch-iommu.txt`

### 8.1 结论一句话
**"结构/实例清单"可参考；"具体地址与中断"高度可疑**（自相矛盾 + 与 msm8916 数值雷同），**不可直接采信**，必须另行取证。

### 8.2 已发现的自相矛盾 / 可疑点（红线）
1. **MDP IOMMU base 两版不一致**：
   - GPT 文档 v1：`0xfd9cc000`（ctx 0xfd9d4000/5000/6000）
   - GPT 深研：`0xfd928000`（ctx 0xfd930000/931000/932000）
   - 差 `0x3A000`。且**两版的 ctx 偏移都恰好是 +0x8000/+0x9000/+0xA000**（模板特征，非"读出"）
2. **五个 IOMMU 的全局中断完全同一组**：mdp/kgsl/venus/jpeg/vfe 全写
   `<0 229 0>,<0 231 0>,<0 230 0>,<0 232 0>` —— 现实中每个 IOMMU 的全局中断独立，**不可能全同**
3. **KGSL ctx 中断 = 241**：而**本树 msm8916 的 `gpu_iommu` ctx 中断正是 241/242** → **疑似照抄 msm8916**
4. 对照件：msm8916 的 ctx 偏移是 **+0x1000/+0x2000**（本树 `msm8916.dtsi`），与 GPT 的 +0x8000 模式不同

### 8.3 用「手机 DTB 实测窗口」做碰撞检测（我方独有证据）
手机 DTB（`msm8994-msft-lumia-octagon-cityman.dtb`）：
- `mdp@fd901000`：`reg = <0xfd901000 0x90000>` → 覆盖 **0xfd901000–0xfd9a1000**
- `mdss@fd900000`：`reg = <0xfd900000 0x1000 0xfd9c8000 0x4d4>`（mdss_phys + **vbif_phys**）
- `gpu@fdb00000`：`reg = <0xfdb00000 0x40000>`
- `dsi-phy@fd998500` / `fd9a0500`

| GPT 声称 | 碰撞检测 | 判定 |
|---|---|---|
| MDP IOMMU `0xfd928000` | 落在 `mdp@fd901000 +0x90000` 窗口**内** | ❌ **不可能**（与 MDP 寄存器区重叠） |
| MDP IOMMU `0xfd9cc000`（v1 版） | 在 `vbif 0xfd9c8000+0x4d4` 之后、不与已知窗口重叠 | ⚠️ **结构合理**（但未证） |
| KGSL IOMMU `0xfdb10000` | 落在 `gpu@fdb00000 +0x40000` 窗口内 | ⚠️ **需要缩小 GPU reg** 才成立（下游可能本就如此） |
| VENUS `0xfdc84000` / JPEG `0xfda64000` / VFE `0xfda44000` | 未与已知窗口冲突 | ⚠️ 合理但未证 |
