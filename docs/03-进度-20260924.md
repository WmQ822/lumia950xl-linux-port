## 结论（比 9-23 更精确）
1. **时钟/电源实际没起来**：
   - `bus` 时钟（= `OXILI_GFX3D_CLK`）**rate = 0** → 父 PLL（`gfx3d_clk_src`）没跑
   - `clk_bulk_prepare_enable` **返回 0**（"成功"）但根本没时钟输出 → 掩蔽了问题
   - `oxili_gx_gdsc` 的供电 `UDD_GFX` **未就绪（rsupply=0K）**；`oxili_cx_gdsc` supply=NULL
2. `ctx_probe` 的**首次硬件访问**（读 `0xfdb18000` 的 FSR）→ **同步外部中止（SError）→ panic**
3. 调用链确认：`deferred_probe_work_func → qcom_iommu_device_probe → devm_of_platform_populate → device_add → ctx probe`（子 ctx 在父 probe 内部被同步拉起）

## 下一步候选（治本）
1. **给 `bus` 时钟显式 `clk_set_rate`**（如下游那样 200MHz）→ 让 `gfx3d_clk_src` PLL 起来，再 enable
2. **确保 GX 供电（UDD_GFX / pm8994 对应 rail）先就绪**：查 `gfx3d`/GDSC 的 supply 依赖链
3. **安全闸**：probe 里若 `clk_get_rate(bus)==0` → 直接 `-EPROBE_DEFER`（至少不崩，留待后续就绪）
4. 核对 msm8994 gcc 驱动里 `gfx3d_clk_src` PLL 是否注册 / 为何 rate=0

## 第二轮：DT 补 `oxili_gfx3d_clk_src` + v4（2026-09-24 20:4x）

### 根因链（三重证据）
1. **下游 8994 DTS**：MMCC 节点 `clock-names` 含 `"oxili_gfx3d_clk"`，`clocks` = `<&clock_rpm clk_oxili_gfx3d_clk_src>` → GPU 时钟源由 **RPM** 提供
2. **我们 5.18 的树**：MMCC 节点只有 `"xo","gpll0"` → 漏掉 gfx3d → `oxili_gfx3d_clk` 父解析失败 = **孤儿时钟（rate=0）**
3. **最新 mainline 已修**：`clock-names` 含 `"mmssnoc_ahb","oxili_gfx3d_clk_src"`，`clocks` 含 `<&rpmcc RPM_SMD_MMSSNOC_AHB_CLK>,<&rpmcc RPM_SMD_GFX3D_CLK_SRC>`
   - 源码：`https://cdn.jsdelivr.net/gh/torvalds/linux@master/arch/arm64/boot/dts/qcom/msm8994.dtsi`
   - 下游 8994：`LineageOS/android_kernel_oneplus_msm8994` / `..._huawei_angler` 的 `drivers/clk/qcom/clock-mmss-8994.c`（`raw.githubusercontent.com` 在寄晴 Debian 上可直连）

### DTB 修复（已刷 → 结果）
- `msm8994.dtsi` 加：`#include <dt-bindings/clock/qcom,rpmcc.h>`；MMCC `clocks`/`clock-names` 补 `oxili_gfx3d_clk_src` → `<&rpmcc RPM_SMD_GFX3D_CLK_SRC>`
- 实测（照片）：**`bus clk: parent=ok rate=2147483647`** → 父时钟挂上了 ✅（rate 是 RPM clk_src 报的 0x7FFFFFFF）
- **但** `ctx_probe` 首访寄存器**依旧 `synchronous external abort: 96000010`** → **缺时钟不是唯一原因**

### v4：对齐新版 mainline（已刷，待验证）
- **关键发现**：最新 mainline `qcom_iommu_device_probe` **已无 `pm_runtime_get_sync/put_sync`**（只 `devm_pm_runtime_enable()` 后直接 populate）
- 我们 5.18 老代码：`get_sync`（上电）→ **`put_sync`（又断电）** → 才 populate 子 ctx → 子设备**在时钟/电源被关状态下读寄存器 → 外部中止**
- v4 改法：**去掉 populate 前的 `put_sync`**，改为 populate 之后才 put（父设备跨 populate 保持 resume）
- 同时 DT 再补 `mmssnoc_ahb`（对齐最新 mainline）
- 产物：`Image` md5 `e28327b920403ee749df6cc937e60b6e`；dtb md5 `d353ad7250c243797a94addf01271c5d`
- 手机备份：`vmlinuz-5.18.0-rc1.bak-v3-20260924`、`...cityman.dtb.bak-dtfix1-20260924`

### ★★★ 重大发现：从手机固件里挖出 ACPI 表（PLAT 分区 `sda34`）
- 位置：`sda34 PLAT`(8M) 里直接有 **DSDT(184851B, OEM="QCOMM MSM8994")**、FACP、SSDT、APIC、GTDT、MCFG（EFIESP 里的 "DSDT" 是误报）
- 已在 CachyOS `/tmp/acpi/` 用 `iasl -d` 反汇编（DSDT.dsl 5 万行）

**ACPI 里 GPU IOMMU 的设备定义（关键！）**
```
Device (GPU0)  _HID="QCOM246F"  _DEP={ MMU0, MMU3, MMU4, PEP0, OMEM, PMIC, DISP, HDDP }
   _CRS: fd900000+CC000(MDSS) / fd828000+108 / IRQ73 / fdb00000+10000(GFX_REGS) /
         fdb20000+1F000(GFX_SHADER_MEM) / IRQ41 / fdc00000+84000 / fdcc0000+40000 / IRQ4C /
         fc4b8000+8000 / GPIO 0x4E
   ※ fdb10000 **不在** GPU0 的 _CRS 里 —— 它是独立设备 MMU3！
Device (MMU3)  _HID="QCOM2400"  _UID=3          ← **GPU IOMMU**
   _CRS: 0xFDB10000 + 0xB000, IRQ 0x46/0x110/0x111/0x112
   GUID: 9833c712-3292-4ffb-b0f4-2bd20e1f7f66（与 GPU0 "MMUIDS" 一致）
   CTXI: 03 00 00 01 ；S2CB(SID→CB): (0,0,0,0)(1,1,0,0)(2,2,0,2) ；XPUE: {01}
其他：MMU0=FD9CC000(MDP) MMU1=FDA44000 MMU2=FDA64000 MMU4=FDC84000(venus)
      MMU5=FDA84000 MMU6=FD864000（每个都有 XPUE 方法）
```
→ **固件自己确认了 GPU IOMMU 就在 `0xFDB10000`**（地址不再有任何疑问），并给出 CTXI/S2CB(SID→CB 映射)/XPUE。

**ACPI PEP（电源引擎插件）里 GPU 组件的上电序列（这就是"Windows 怎么做的"）**：
```
FSTATE2 / ENTER:
  CLOCK: oxili_rbbmtimer_clk   ← v15 证实它原本是关的
  CLOCK: oxilicx_ahb_clk
  CLOCK: oxili_gfx3d_clk
  **BUSARB: ICBID_MASTER_APPSS_PROC → ICBID_SLAVE_GFX3D_CFG**   ← 关键！AP 先对该从端口投票
  FOOTSWITCH: VDD_OXILI / VDD_OXILICX
  REQUIRED_RESOURCE: (1, "/clk/oxili", 0)
EXIT: 逆序 + BUSARB(0x11E1A300)
```
- 对照：下游 `msm8994-bus.dtsi` 里有 `qcom,msm-bus-device`（reg: `0xFC460000 0x5880` + snoc/bimc/pnoc/mnoc/cnoc 基址）→ 8994 的 NoC 是 **AP 可直接编程的 QoS 寄存器** + RPM 时钟；下游 kgsl_iommu 的总线投票是 `<26 512>`（APPS→EBI）
- **结论：固件指出我们只差最后一项 —— `BUSARB`（AP→`GFX3D_CFG` 的 NoC 投票）+ XPU 权限**；这也完美解释"写被丢弃、读报错"（NoC 到该从端口的路没打开）

### 下一步候选（按性价比）
1. **"Windows 热重启"旁路实验**（低成本）: 先在 WOA(仍装在 MainOS) 里启动，再**热重启**进 Linux，看 NoC/XPU 状态是否被保留 → 若保留，fdb10000 立刻可读，且证明"是运行期配置问题"
