## 一、侦察结论（关键新事实）

1. **本机内核没有任何 msm_bus / ICB fabric 驱动**
   - `drivers/interconnect/qcom/`：只有通用 `icc-rpm` / `bcm-voter` / `icc-osm-l3`，**没有 msm8994 fabric/bus 驱动**
   - `drivers/bus/`：无 `msm_bus`
   - ⇒ **根本没人给任何 NoC 编 QoS**。所以"照 msm_bus 布局写 QoS"这条路：
     ① 没有参照驱动可抄 ② 即使写，也只能写**可读的 SNOC/BIMC/CNOC**，而 mnoc 的 QoS
     寄存器在**暗区写不进去**。⇒ **纯 QoS 直写对"唤醒 mnoc"无用。**

2. **mnoc 的 bus clock 链（来自 caf-bus.dtsi `fab_mnoc`）**
   - `fab_mnoc` 时钟 = `clk_mmss_s0_axi_clk`（MMCC CBCR **0x5064**，BIT0）
   - `mmss_mmssnoc_axi_clk` = MMCC CBCR **0x506c**
   - 二者父 = `axi_clk_src`（MMCC **CMD_RCGR 0x5040**），父可选 **gpll0(sel=5) / mmpll1(sel=2)**
   - MMCC base = **0xfd8c0000**（reg 0x40000）

3. **"使能但没在跑"现象**：v6c 读到 GFX3D_CLK `EN=1 RUN=0`（bit0=1 但 bit31=0）
   ⇒ 分支开了但源头 PLL/RCG 没转 —— 高度怀疑 mnoc 的 axi 链同病：**总线没时钟 → external abort**。
   这与"MDSS/GPU 亮、mnoc+全 IOMMU 暗"的明暗地图自洽（MDSS/GPU 走别的时钟源）。

## 二、v31 做了什么（已编译通过）

文件：`drivers/iommu/arm/arm-smmu/qcom_iommu.c` → `mo_late_work()`，插在危险读（v7）**之前**。
（铁律沿用：危险读永远最后）

- **v31 段（安全，MMCC 活块）**：
  1. **全量 dump MMCC 时钟链**：mmpll0/1/3/4 寄存器（0x0~0x100）+ RCG/CBCR 区（0x502c/0x5040/0x5044/0x5064/0x506c…）
  2. **强制点亮**：`axi_clk_src` 根(0x5040) + `mmss_s0_axi`(0x5064) + `mmss_mmssnoc_axi`(0x506c) + `mmss_misc_ahb`(0x502c)，逐条 before/after + 判 en/run
  3. **兜底**：若 s0_axi `EN=1 但 RUN=0` → 把 `axi_clk_src` 父切到 **gpll0(sel=5)**（gpll0 必活），再判 run
- **v31b 段**：可读 fabric（SNOC/BIMC/CNOC）QoS 寄存器**只读**探底，为后续 QoS 直写找落点
- **v29/v30 读表追加**：`{0xfc47b000, 68000}` = **mnoc fabric base（+0x3000）** —— 在时钟强制点亮**之后**的错峰读里复测 mnoc 是否变可读

判定逻辑：
- 若 +62s/+68s 那两个 mnoc 读**变可读** → 时钟链就是根因，继续扫 mnoc 结构（xPU/QoS 端口）
- 若仍 abort → 转 9-25 的 **备选 A（RPM 侧 ICB 投票）** 或 **备选 B（xPU/TZ 授权）**

## 二·五、v31 实机结果（寄晴 17:10 部署 → 17:20 读日志）★

### 结果 A：v31 的时钟强制段**没跑**（插补丁位置踩雷）

### 结果 B：★★ mnoc 其实是“活的”——+0x3000 可读！
```
[v29] READ fc478000 ...        (无值 -> abort)
[v29] fc47b000 = 0xe3d3c004    ← mnoc fabric base(+0x3000) 读成功！
```
- `0xFC478000`（+0）= 地址空洞（unimplemented）→ 一读就 abort
- **真正的 fabric 寄存器在 +0x3000 = `0xFC47B000`，可读！**
- ⇒ **“整片 MMSS NoC 暗”这个结论可能是被“读 + 0 就 abort”误导的**（v27 在第一个偏移就挂，根本没走到 +0x3000）
- ⇒ 根因**可能不是“NoC 没唤醒”**，而是各 MMU0~4 自身的时钟/权限，或 xPU

### 结果 C：其它
- 6 个 IOMMU/NoC 地址各自 abort（123.9/130.0/136.2/142.3/148.5/154.6s），但都是**独立 kthread 挂掉**（错峰设计生效，系统存活）
- 361s 处 `qcom_iommu_attach_dev+0x268` NULL 解引用 oops（adreno 加 iommu group 那段）——独立 bug，另有账

## 二·七、v32 实机结果（寄晴 17:30 部署 → 17:37 读日志）★★ 方向修正

**所有同步段跑通（顺序修好）**；关键结果：

### ★★ 1. MMSS NoC 是【活的】——“整片 NoC 暗”彻底推翻了
```
fc47b000 = 0xe3d3c004    ✅
fc47b040 = 0x00000000    ✅
fc47b080 = 0x9d254504    ✅
fc47b100 = 0x3b822704    ✅
fc47b180 = 0xc85e8004    ✅
```
→ **mnoc fabric 寄存器 (+0x3000~) 全部可读**。之前的“mnoc 不可达”纯粹是**读了 +0 的地址空洞**（0xFC478000 未实现）导致的误判。

### 2. 时钟链其实一直是对的（“RUN”判读又又又踩坑）
```
0x5064 mmss_s0_axi     = 0x20008001  (bit0=1 使能, bit31=0 => 未停 = 在跑)
0x506c mmss_mmssnoc_axi= 0x00000001  (在跑)
0x502c mmss_misc_ahb   before 0x80008000(bit31=1 停) -> after 0x20008001(在跑)
0x5044 axi_clk_src CFG = 0x00000503  (src_sel=5 => 已经就是 gpll0)
```
→ **bit31 = BRANCH_CLK_OFF（1=停）**，CBCR bit31=0 就是“在跑”。**上次拿 bit31 当 RUN 又读反了（坑#4）**。
→ **MMSS NoC 的 AXI 时钟一直是通的，源头 gpll0 也对**。⇒ 时钟不是阻断点。

### ★★ 3. 真正的阻断点 = 5 个 IOMMU 寄存器窗口（MMU0~4）
```
✅ 活：MDSS_MDP(fd900000)、GPU(fdb00000)、QFPROM、SNOC(fc460000)、MNOC(fc47b000+)
❌ 死：fd9cc000(MMU0)、fda44000(MMU1)、fda64000(MMU2)、fdb10000(MMU3/GPU IOMMU)、fdc84000(MMU4)
```
→ **同一子系统里“引擎活着、它的 IOMMU 却死”**（MDSS 活/MMU0 死；GPU 活/MMU3 死）
→ 高度指向 **xPU / 防火墙**：SMMU 寄存器窗口被 TZ 保护，AP 未授权就 external abort。
   证据链：ACPI 里 `MMU3` 带 `XPUE={01}`；TZ.bin 含完整 xPU HAL；“引擎活/IOMMU 死”符合“窗口被单独保护”而非“子系统断电”。

### 4. SNOC QoS 寄存器可读
```
SNOC +0x5000=0x5  +0x5080=0x36078a04  +0x5100=0x88227d04  +0x5180=0xb3f25404
```
→ QoS 通道本身没问题，但**够不到 IOMMU**（IOMMU 不在 Its QoS 路径）。

### ⇒ 结论：
- **首选（NoC/QoS 直写）已排除**（NoC 好好的）
- **方向转到备选 B：xPU / TZ 授权**（与 ACPI XPUE + TZ xPU HAL 完全对口）

## 二·八、v33 判别实验结果（寄晴 17:44 部署 → 17:51 读日志）★★ 定性

**读表：7 个 MMU 全灭，邻居全活。**
```
✅ 活：DISP(fd900000)=0x10090000 · GPU(fdb00000)=0x00010011 · GPU第二窗口(fd828000)=0x0
      · MNOC(fc47b000/40/80/100/180) 全可读 · SNOC QoS 可读
❌ 死：MMU0(fd9cc000) MMU1(fda44000) MMU2(fda64000) MMU3(fdb10000/12000/18000/1a000)
      MMU4(fdc84000) MMU5(fda84000) MMU6(fd864000) · 空洞对照(fdf00000)
```
- **MMU3 三段全死**：global(0x0)、+0x2000、ns-ctx(0x8000)、sec-ctx(0xa000) —— **不是“只有 secure 段锁”**
- **7/7 SMMU 窗口一律 abort**，而**相邻的 GPU 窗口/显示器窗口全部可读**
- abort 综合症与“空洞”一致（均为 `synchronous external abort 96000010`）

### ⇒ 判定：
1. **不是全局时钟/电源问题** —— 相邻同域窗口全部活着（DISP 活 / MMU0 死只差 0xCC000 边界）
2. 所有 SMMU 行为**高度一致**（全灭），指向两类共同因子：
   - **(a) SMMU 专属总线时钟没真跑**：`[late] bus clk rate=2147483647`（INT_MAX）是个**红旗**（GPU IOMMU 的 "bus" = OXILI_GFX3D_CLK）
   - **(b) TZ/xPU 把这 7 个 SMMU 窗口登记为 secure/防火墙** —— “已实现但不可访问”且与空洞同症状，符合“被防火墙挡住”（参考 ACIA XPUE + TZ xPU HAL）
3. 尚不能 100% 区分 (a)/(b) —— 但 (a) 更可测、更便宜

  - **效果**：只有 MMU3 的 **NS 段**（`fdb12000=0x8`、`fdb18000=0x0`）从 abort → 可读；`fdb10000`(base+0)、`fdb1a000`(sec-ctx) 仍锁；**MMU0（fd9cc000）交了 `sec_id=1` 后仍旧 abort**
  - ⇒ **TZ 交权调用可用且安全（部分 id），但“解锁”目前只在 MMU3 生效**；其它 MMU 的 sec_id/方式待继续
- **迭代教训**：①危险读必须最后 ②多个同步“雷”会早死——关键实验放函数最前 ③**SCM 盲扫 sec_id 会卡死 SoC**，必须逐个、调用前先落盘 ④写 Python 打补丁时注意 `\n` 转义
